# Drive Roadster World 設計案

更新: 2026-10-17 / 状態: 実装前の設計。Unityビルド・VRChat実機・複数人同期は未検証。
想定リポジトリ: `Xenoah/vrcworld_drive-roadster`

## 1. 目指す体験

低く流麗な電動スポーツカーで、地上の高速走行、壁面への乗り移り、空中のリング通過が連続する体験。精密なコックピットで「運転している」感覚を作り、フリー走行とタイムアタックを遊べるPC/PCVRワールドにする。

Tesla新型Roadsterの雰囲気を参考にしたオリジナル車両を制作する。実車の正確な再現、メーカー公認、未発表仕様の再現は標榜しない。飛行・壁走りは本ワールド独自のゲーム能力。公式画像は外観研究に用い、配布モデル・テクスチャ・ロゴとして無断転載しない。

PC/PCVR優先は暫定。Quest単体対応、同時運転人数、車両の商標・名称方針は実装着手時に確定する。最初から大規模マップや多数の車種を作らない。

## 2. 最初の完成単位

最初の縦切りは「1車種、1台の共有車両、1本の完成度の高い周回コース」。2人以上で乗車権・観戦・交代を試せる状態まで作る。運転の楽しさと安定性を確認後、同じ車両Prefabを4台の事前配置プールに拡張する。1車種と1台は区別する。

### 含めるもの
- 外装・前席コックピット・タイヤ・ライトまで整えた1車種
- 運転席1席。助手席は同期基盤が安定してから追加
- 発進、制動、後退、操舵、限定壁走り、アシスト飛行、着地、復帰
- 90～150秒程度を目標とする短い周回コース（所要時間は試走で決定）
- フリー練習と、同コースの個人タイムアタック
- 周回有効性、自己ベスト、インスタンス内の参考ランキング
- 途中参加、運転者離脱、転倒・落下復帰、車両交代
- フレーム時間・通信量・同期誤差を確認する開発用表示

### 後回し
- 大規模オープンワールド、一般交通、AI対戦、破壊表現
- 車体同士の競技接触、接触あり同時レース、車種追加、チューニング
- 世界共通の信頼できるオンラインランキング
- Quest最適化、雨天や昼夜の動的切替、外部サービス連携

## 3. 見た目の品質基準

### 車両
- 低いノーズ、張りのあるフェンダー、滑らかなキャビン、明確な後輪の存在感を軸に独自プロポーションを作る。
- シルエット、ホイールベース、タイヤ径を先に確定し、細部で形の弱さをごまかさない。
- ボディ塗装、ガラス、ゴム、金属、室内素材の粗さと反射を分離する。
- ヘッドライト/テールライト内部、ブレーキ、ホイール、パネルの継ぎ目、座席縫い目は視認距離に合わせてメッシュと法線で使い分ける。
- ドライバー視点のダッシュボード、手前のステアリング、足元、Aピラーの品質を外装同等に重視する。
- HUDは速度、走行モード、次のチェックポイント、経過/差分タイム、周回無効理由に絞る。
- 発光で速度を伝えるが強い点滅、視界を塞ぐ粒子、常時ブルームに依存しない。
- LOD、衝突用簡易形状、編集可能な原本、書き出しデータを別管理する。

### コース
舞台は海岸沿いの近未来テスト施設。昼の斜光、白～淡灰色の路面、暗い岩、控えめなシアンの誘導で車両が映える背景を作る。

1. 安全なパドック: 操作説明、車両選択、快適性設定、ランキング
2. 地上加速区間: 見通しのよい直線と制動目印
3. 高速コーナー: 速度感とグリップを体験
4. 壁走り区間: 十分に長い曲面の導入と出口。突然90度に折れない
5. 離陸区間: 明瞭なゲート、空中リング3個程度、広い着地帯
6. 減速区間: 着地後の姿勢回復余地と最終コーナー
7. フィニッシュ: 記録表示後、そのまま再周回またはピットへ

走行方向は色だけでなく矢印、路面帯、ゲート番号、音で伝える。失敗時に次の進路が分からなくならないよう、復帰地点からも案内を確認できる配置にする。フリー練習パッドは競技ラインと離す。

## 4. 車両挙動

車体は単一Rigidbodyを基準に、運転者のクライアントだけが物理を計算する設計。4点のサスペンションレイを初期候補とし、VRChat/Udon対応API・接地安定性・負荷を実機で確認する。WheelCollider等との比較は必要なときだけ行い、実装方式を先に過剰固定しない。

状態: `Parked → Grounded ↔ WallRide ↔ AssistedFlight → Recovery`。乗車権/接続状態は走行状態と別に持つ。

- 地上: 低速では操作しやすく、高速では操舵量を抑える。グリップと制動は楽しいアーケード寄り。
- 壁走り: 専用路面だけで有効。複数の接地サンプルから法線を平滑化し、吸着力・姿勢制御を制限する。入口速度、接地の継続時間、出口離脱条件を定義し、継ぎ目の瞬間誤判定を抑える。
- 飛行: 専用区間で操縦モードに入り、ピッチ/ヨーを制限した姿勢アシストを基本とする。際限のない上昇・飛行でコースを省略できないよう領域と経路を定義する。
- 着地: 接地確定までは飛行制御を急に切らない。重複する接地/浮上判定にヒステリシスを持たせる。
- 脱輪/転倒/落下: 自動判定と手動リセットを用意。競技中の復帰はその周回を無効にし、タイマーも明示的に終了する。
- スポーン: パドックの固定スロット。復帰先が塞がっているときは安全位置を選び、他車の中へ出現させない。

入力アダプターを車両物理から分離する。デスクトップとVRで同じ論理入力（加速、制動、操舵、モード、復帰）を供給し、実際のキー/ボタン割当とStation内入力はSDKと実機で検証する。物理ハンドル操作は初期必須にしない。

## 5. VR快適性

- 初回は低速練習、飛行/壁走りの事前説明、いつでも退出できる導線を用意。
- 通常Station着座を第一候補にし、プレイヤーの頭をスクリプトで強制回転させない。
- 追加の画面揺れ、カメラロール演出、モーションブラー、急なズームを使わない。
- 安定した車内フレーム、緩やかな加速度変化、広い旋回半径を基本にする。
- 速度制限・アシスト強度・音量・エフェクト抑制を選択可能にする。競技上の物理差を生む設定は記録クラスを分ける。
- 水平視界保持や独立座席回転はStation/アバター姿勢と矛盾する可能性があるため、実験項目。実装できると約束しない。
- 高速中の降車は安全な退避位置へ戻す設計。通常退出と緊急復帰を実機で確認する。
- VR酔いは個人差が大きい。快適性を保証せず、複数人の短い試走で評価する。

## 6. マルチプレイと権限

### 所有者と状態の一本化
車両ごとに1人の有効運転者と1つの権威状態を持つ。運転者が車両物理・車両同期の所有者となる設計を基本にする。ObjectSyncのTransform同期と独自Transform同期を同時使用しない。同期方式は初期試作で比較後に1つへ決める。

状態スナップショットの候補:
- 車両スロットID、状態世代番号、運転者playerId、占有状態
- 走行モード、復帰番号、コースID、走行セッションID
- 次チェックポイント、周回有効性、開始時刻、終了記録
- 表示に必要な操舵/車輪速度/ライト等の低頻度データ

Transform/速度などの高頻度情報と、乗車・周回結果などの低頻度情報を分ける。ホイール4本のTransformを個別同期せず、見た目の回転は各クライアントで再構成する。

### 乗車競合
1. 空席表示から乗車要求を送る。
2. 現所有者または専用の管理オブジェクトが空席と要求者を確認する。
3. 所有権・世代番号・予約者を更新し、確定を待つ。
4. 権限取得が確認できた本人だけ運転を開始する。
5. 競合の敗者は車両を動かさず待機する。所有権取得を要求しただけで成功扱いにしない。

具体的な要求配送とStation占有の整合はSDK検証で確定する。複数クライアントが同じ車両を同時に物理制御する状態を最重要の禁止条件にする。所有権要求を無条件許可しない。

### 遠隔表示
非所有者では物理を独立駆動しない。同期の補間を使い、遠隔車の見た目を滑らかにする。必要な推測補間は短時間に制限し、情報が止まったら暴走させない。復帰時は補間履歴を破棄し、新位置へのワープを明示する。

### 退出・切断・途中参加
- 運転者の降車/切断: 入力停止、走行を無効化し、権限移譲完了後に一度だけ安全復帰。
- 所有権移譲途中: 書き込みを止め、世代番号で古い更新を除外。自動移譲先を運転者として扱わない。
- 途中参加: 過去のイベント再生に頼らず、同期変数の現在値から占有・位置・周回・ランキングを再構成。
- 車両管理者切断: 新所有者が現在のプレイヤーと占有状態を突き合わせ、空席を修復。
- playerIdの再利用/別走行との混同を避けるため、ID単独でなく走行セッションIDも照合。
- 助手席追加時: 座席ごとの占有を独立管理し、助手席操作で車両所有権を奪わない。運転者退出時は同乗者を安全に戻す。

ネットワークイベントは通知用、同期状態は復元用に分ける。インスタンスMasterを恒久的な信頼サーバーとみなさない。

## 7. フリー走行とタイムアタック

初期は同じ車両とコースを利用するが、競技の成立は走行単位で管理する。フリーモードから走りながら競技モードへ切り替えられない。スタート区画で停止して明示的に開始し、同一の初期位置・速度から計測する。

4台に拡張後、個人タイムアタック中の車両同士は非接触を基本とする。外部車両に妨害されないよう、車両用レイヤー/衝突マトリクスを検証する。フリー用の練習エリアと競技入口を空間的に分離し、歩行者がコースへ入っても物理妨害にならない設計にする。

### 有効周回
- コースバージョン、車両物理バージョン、アシストクラスを記録に含める。
- スタートの前に走行セッションID、次ゲート番号、開始時刻、記録状態を初期化。
- ゲートは順番・方向・車両本人・セッションIDを検査し、同一ゲートの二重計測を防ぐ。
- 高速で薄いTriggerを通過しても抜け落ちないよう、前後位置のゲート面交差と領域判定、または十分な厚み＋物理検証で対策する。
- 飛行リング、壁走り出口、着地点に必須ゲートを設け、コーナーの短絡を防ぐ。
- ゲート間の許可領域、必要走行モード、極端な最短到達時間を補助検証する。閾値は推測で厳格化せず実走データから決める。
- リセット、テレポート、ドライバー変更、途中切断、モード/物理設定変更、領域逸脱は無効。
- 無効理由を表示し、練習走行を続けるか再スタートを選べる。
- 最後の必須ゲートを通った有効セッションだけ終了記録を確定する。

### 計測とランキング
計測は共通時間基準を用いる候補だが、APIと精度はSDK検証で確定する。表示フレームごとの加算でタイムを作らない。結果は一度だけ確定し、同じセッションの再送を重複登録しない。

最初は本人のセッションベストとインスタンス内上位10件を表示する。個人の永続記録は対応APIの確認後に追加。クライアント側Udonの検証は通常のショートカット抑止であり、改造クライアントまで防ぐ信頼できるアンチチートではない。「参考記録」と明記し、世界共通の競技ランキングを保証しない。

記録管理オブジェクトの所有者が結果を直列に反映し、途中参加には同期済み一覧を渡す。管理者移譲の際は一覧と世代を保持し、未確定結果の安全な再送を許す。運転車両ごとの結果スロットを候補とし、全員が同じ配列を書き換える構造を避ける。

## 8. 初期性能予算（公式制限ではなく設計目標）

対象実機・ヘッドセット・解像度・アバターを固定して計測する。5950X/RTX 3070という型番だけでVR性能を保証しない。

- 90Hz VRを検証基準の一例とし、総フレーム11.1ms以内が目標。CPU/GPUを別計測し、アバターの負荷余地を残す。
- 初期テストは1台、拡張判定は4台＋8人。人数上限を先に大きくしない。
- 車両LOD0: 80k三角形以内を初期目標、LOD1 30k、LOD2 8k程度。コックピット近接品質に必要なら計測根拠付きで調整。
- 車両マテリアル: 6～8程度を出発点。小部品ごとの材質増殖を避ける。
- 主テクスチャは2K中心。4Kは実画面で差が出る箇所に限定。テクスチャの実メモリをProfilerで記録する。
- 車体コライダーは簡易複合形状。走行路は連続で滑らかな衝突面とし、装飾メッシュをそのまま衝突に使わない。
- 静的環境はベイク照明中心。常時リアルタイム反射、全車の影付きライト、広範な透明面を避ける。
- 音・粒子・遠景・遠隔車の更新を距離で制限。非稼働車の高頻度更新を停止。
- 通信頻度は数値を決め打ちせず、SDK制約と実測通信量/混雑を基に調整。位置同期と毎フレームの手動Serializationを併用しない。
- 最終的には「4台が同時に壁走り/飛行する最悪区間」でCPU/GPU/GC/通信の95パーセンタイルと最大値を記録する。

## 9. 実装構成案

- `VehicleInput`: デスクトップ/VRの論理入力
- `VehiclePhysics`: 所有者だけの走行・壁走り・飛行制御
- `VehicleSession`: 所有権、座席、状態世代、退出と復帰
- `VehiclePresentation`: ホイール、ステアリング、音、ライト、LOD
- `CourseDefinition`: コースID、版、ゲート順、許可領域、復帰先
- `RunController`: 計測、有効判定、再走行
- `InstanceLeaderboard`: 参考記録の集約と同期
- `ComfortSettings`: ローカル表示設定と走行クラス
- `Diagnostics`: 所有者、セッション、ゲート、同期状態、負荷の表示

Prefabの階層と同期境界を先に図示してからUdonSharpを作る。Unity生成物のYAMLを手書きで量産せず、Editor上で検証可能な生成/セットアップ手順を用意する。

## 10. 制作順と完了判定

### A. 環境・グレーボックス
対応Unity/SDKを公式で確認しVCCプロジェクトを作成。単純な車体で地上周回、ブレーキ、復帰を確認。ビルドログと操作動画を残す。

### B. 同期・座席
1台で2～3クライアント検証。同時乗車、途中参加、所有者退出を先に潰す。ドライバー以外が物理更新しないことをログで確認。

### C. 壁走り・飛行
専用小コースで遷移と快適性を検証してから本周回に接続。落下・転倒から必ず戻れることを確認。

### D. 計測
順序ゲート、逆走、ショートカット、リセット、二重フィニッシュ、再走行を検証。成立していない走行が記録されないこと。

### E. 見た目と音
完成形の車両とコースへ差し替え。差し替え前後の物理・描画負荷を比較し、近景の品質を仕上げる。

### F. 4台負荷・公開前検証
共有プール拡張、助手席の必要性判断、実機VR試走、途中参加/退出の反復。ビルド・同期・快適性・性能の証拠が揃ってから公開準備へ。

## 11. テスト一覧

| 分野 | 必須ケース | 合格条件 |
|---|---|---|
| 基本走行 | 発進/停止/後退/高低速操舵/斜面 | 制御不能・NaN・地面貫通がない |
| 壁走り | 入口、低速脱落、継ぎ目、出口、逆進入 | 状態が高速振動せず安全に復帰できる |
| 飛行 | 離陸、連続入力、領域外、着地、失速相当 | 無限加速/無限上昇せず着地が安定 |
| 所有権 | 同時乗車、退出中の乗車、所有者切断 | 有効運転者が同時に2人にならない |
| 座席 | VR/PC乗降、緊急退出、助手席追加時 | 視点/アバター/占有状態が破綻しない |
| 途中参加 | 走行中、復帰中、結果表示中に参加 | 現在状態が復元され空席と誤認しない |
| 周回 | 正順、逆順、逆走、ゲート飛越し、二重接触 | 正規走行のみ一度だけ記録 |
| 再走行 | 完走→再走、無効→再走、車両交代 | 前セッションのタイマー/ゲートを引き継がない |
| 通信 | 実測遅延、低FPS、短い停止、所有者移譲 | 遠隔暴走なし。復旧時に誤記録なし |
| 快適性 | PC/VR、速度変更、壁→飛行→着地 | 追加の視点演出なし、退出が常に可能 |
| 性能 | 1/4台、8人、最悪カメラ位置 | 実測予算内。超過は公開前に削減 |
| 配布 | 新規checkoutから復元、依存/原本/ライセンス | 秘密情報なし、参照欠落なし、ビルド手順再現可能 |
